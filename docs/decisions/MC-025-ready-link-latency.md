# MC-025 ready-link latency implementation

User approved implementation on 2026-09-26, targeting typical full request/reply RTT below one second on a ready direct connection. Physical results remain pending. This decision changes local key representation and encoder selection, not wire bytes, pacing or trust requirements.

## Protected Android storage

Version 1 wrapped a random 64-byte binary SQLCipher passphrase. Version 2 wraps 64 bytes: AES key (32), database salt (16), reserved zeros (16). AAD remains the version byte plus the 16-byte identity generation. The existing unlocked-device Keystore wrapping alias, per-operation identity lock, connection closure, unlock recheck, reset journal and backup exclusion remain unchanged. No clear key or database handle is cached between operations.

New stores use random key/salt material. On legacy reopen, validate the database and its native generation with the old passphrase; require SQLCipher v4 settings (256000 KDF iterations, PBKDF2-HMAC-SHA512, HMAC enabled with SHA512, 4096-byte pages, zero plaintext-header bytes). Read the existing 16-byte file salt after journal recovery. Derive the identical AES key once, open the same database with the documented raw key-plus-salt byte argument, and validate the native store again. Only then, under unlock checks, atomically replace the wrapped envelope. Neither validation performs retention pruning; the ordinary subsequent operation retains normal retention behavior.

This replaces the earlier possible encrypted-copy migration. No database rekey, export, copy or rename occurs. Before the atomic envelope commit, version 1 still opens the same database; after it, version 2 does. A write/fsync exception may leave either envelope and the operation fails; reopening validates whichever durable envelope survived. Seal, authentication, generation, configuration or validation failures do not replace the envelope or silently recreate history. An old app rejects version 2; downgrade requires an explicit compatible recovery path, never automatic reset. Existing reset deletes both envelope versions through the same guard.

Derivation uses pinned RustCrypto `pbkdf2 0.13.0`, defaults disabled and HMAC enabled. Its only dependencies reuse existing `digest 0.11.3` and `hmac 0.13.0`; SHA512 comes from the existing `sha2 0.11.0` dependency. The crate supports Rust 1.85 and MIT/Apache-2.0; no PHC/password-string, random, parallel or additional hashing features are enabled. Application-owned key buffers are cleared; native input/output temporaries use `Zeroizing`. FFI serialization and library internal copies retain their existing runtime limitations; this is not proof that every transient memory copy is erased. Independent platform security assessment remains required.

Sources: [SQLCipher key API](https://www.zetetic.net/sqlcipher/sqlcipher-api/#PRAGMA_key), [SQLCipher design](https://www.zetetic.net/sqlcipher/design/), [RustCrypto PBKDF2 API](https://docs.rs/pbkdf2/0.13.0/pbkdf2/). Binary known-answer tests include zero and high-bit bytes; a text-password API would alter these secrets and cannot replace the binary derivation.

## Negotiated encoder capacity

Native links start the scheduler at 146 bytes for HELLO. No other object can enqueue before admission. After both the peer HELLO and local HELLO completion, one admission transition sets the encoder ceiling to the effective transmit capacity: the minimum of measured local transmit and peer receive capacities. The receiver retains its own effective directional limit. This activation refuses queued or in-flight objects, unknown/stale handles, invalid capacities and repeated activation. It changes only encoder capacity and the one-time flag; buckets, deficits, transfer sequence, readiness and the next-send deadline are preserved.

An admitted native capacity change still tears down the generation. A requested MTU, INFO maximum or a faster test result never substitutes for measured directional capacity. The wire format and HELLO fields are unchanged, so older conservative senders remain compatible. A 146-byte direction remains fragmented; larger directions may fit a whole logical message. Every actual frame remains charged and paced at one frame/second/link, including HELLO, proof, announcements and catch-up. No immediate send is promised when ordinary control traffic consumed that interval.

## Acceptance and limits

Local checks cover binary derivation, real SQLCipher migration with synthetic data and fault injection, new-store reopening, directional framing, queued/in-flight refusal, stale generations and unchanged scheduler attempts. Emulator evidence is not Keystore hardware certification or physical Bluetooth interoperability. Android and iOS consume the changed shared core; Mac/Xcode native validation remains pending on this Windows host. Paired latency, real lock/key-loss/reset recovery and battery runs remain pending until hardware is available. The predeclared [experiment](../testing/MC-025-subsecond-feasibility.md#proposed-acceptance-experiment) accounts for every scheduled attempt and requires a median below 1000 ms; no such result is claimed yet.
