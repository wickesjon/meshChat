# Android organizer workflow

MC-030 connects the Android event screens to the canonical organizer verifier and the shared native transport. EVENT_INFO is a discovery hint only. Open **#event updates**, select **Scan official QR**, compare the event name, full root fingerprint and expiry against an official source, then explicitly adopt. Public event links also open the same inert confirmation. A staff code never adopts a root.

Under **Event & staff keys**, scan a private staff QR from the offline organizer console. The app shows the credential label, event identifier and exact validity before confirmation. It validates the root signature, adopted root, validity and seed/public-key binding before replacing the current device credential. A failed validation preserves the previous credential. One active staff key is stored per Android installation; multiple event roots remain supported. Expired, not-yet-valid or unadopted credentials cannot post. Forgotten/lost/invalidated keys require explicit reprovisioning. Reprovisioning does not revoke a leaked credential before its signed expiry.

Private scanning uses a separate, non-exported activity. Private results do not enter result intents or saved activity-result state. The scanner and confirmation use Android's secure-window flag; Activity and dialog windows reject full and partial obscured touches. The application does not export, copy, log or save private QR images. Pending private input is discarded on cancellation, background and after one minute. Android/JVM/camera components can retain transient copies; these controls do not establish complete process-memory erasure or protection against a compromised device or an external camera. The MC-043 physical protection scenarios remain mandatory before sensitive-data use.

A dedicated AndroidKeyStore AES-GCM wrapping key protects the credential under the app's no-backup directory. Its authenticated header binds it to the current identity generation. Each signing operation opens the envelope, imports into a short-lived canonical Rust staff session, signs, invalidates the session and clears the mutable plaintext buffer. Background notification immediately closes the native staff-submission gate, independently of queued UI work; foreground resumption cannot revive a gate closed by a newer lifecycle notification. Identity reset also deletes the staff wrapping key/envelope under the existing reset lock. Interrupted creation/deletion and missing keys fail closed; the UI offers explicit forget/reprovision recovery. Replacement uses an atomic envelope write. No private staff data is stored in ordinary settings or the public credential cache.

Staff keys and Beacon Mode cannot be enabled together through the application. Forget the staff key before turning on manual or automatic Beacon Mode. Beacons and other non-adopting phones still relay public signed updates and cache public credentials without acquiring signing authority.

With an adopted current root, valid current chains get a separate **Event Staff** badge. Other event messages are available in a collapsed, bounded unverified drawer. Without an adopted current root, the channel remains open and explicitly warns that event claims can be spoofed. Pin controls sign the pin state and expiry; the UI rechecks root/credential/pin expiry at display, and the native owner rechecks authority on every outgoing fragment. Credential recovery uses the existing bounded cache, CRED_REQ retries/deadline and CRED_OFFER schedule. Offers occur on active launch, first post and every five minutes while active.

Authenticated history now retains the local root adoption revision alongside its existing public provenance. Root removal/re-adoption cannot resurrect an old authority token or pin. Older pre-UI records without this revision remain readable without a current badge or pin. This changes local evidence only; canonical wire formats and public credential bytes are unchanged. Replay/conflict records still control acceptance, and historical display never reapplies an accepted effect.

Tests use generated synthetic credentials and in-process frame delivery. Android emulator evidence is distinct from physical Bluetooth/OEM behavior, screenshot/backup resistance on supported handsets, and independent security review. Those remain assigned to MC-025/027/043/044 and the independent assessment gates.
