# MC-026 iOS CoreBluetooth driver

## Ownership and application entry

`src/ios/BLE/Transport/IOSGattRadio.swift` is the production CoreBluetooth adapter. The existing BLE probe remains a separate synthetic UI; its project compiles the production sources and generated Rust bindings in both device and simulator builds. MC-035 owns application feature/UI integration. No production connection is started by the probe UI.

The application opens its protected store, obtains public identity metadata, constructs `NativeTransport.newIos`, and supplies that core to `IOSGattRadio`. Start must follow an authorized application entry with protected data/provider availability. The radio retains neither an unlocked identity session nor a plaintext fallback. `proof` accepts a short-lived identity session and invalidates it on success, failure or stale connection. The application supplies authorized protocol-owner egress and consumes transport events. Native acceptance never proves peer delivery, authenticated display or history acceptance.

The foreground catch-up callback asks the existing feature/SYNC owner to initiate its bounded request. `enqueueSync` carries only an already-authorized, structurally valid SYNC item/marker through the existing scheduler. Incoming wrappers remain `DeferredSync`; the application must bind them to the active session/direction and finish ordinary content/crypto acceptance. This adapter neither starts arbitrary history walks nor treats native submission as SYNC completion.

## Capacities and flow control

Both roles use the production service/TX/RX/INFO UUIDs from MC-006. INFO remains exactly `01 02 00`. The central validates INFO and characteristic properties before enabling notifications and starting HELLO. The peripheral supplies the fixed INFO value and requires a subscribed RX characteristic before accepting that central's writes. Advertising contains only the service UUID.

The central queries `maximumWriteValueLength(for: .withoutResponse)` and the peripheral queries each subscriber's `maximumUpdateValueLength`. Each actual native transmit limit is capped at the protocol ceiling 512; below 146 refuses. The advertised local receive ceiling is the bounded 512-byte receiver, not a claimed negotiated MTU. HELLO supplies the peer's independent transmit/receive limits; the shared scheduler conservatively encodes at the already-approved 146-byte floor. Changes to observed native capacity close the logical generation.

CoreBluetooth write-without-response has no per-write completion callback. The driver checks `canSendWriteWithoutResponse`, submits on the serialized main queue, and reports OS submission to Rust immediately. It never waits for `didWriteValueFor`. A false notification `updateValue` pauses that peripheral manager's sends until `peripheralManagerIsReady(toUpdateSubscribers:)`; it does not advance the fragment or count a native failure. A new actual attempt pays new credit through the existing scheduler, without resetting object deadlines, pacing, budgets or object ordering. Repeated queue-full results cannot trigger the Android two-failure rule. No frame bytes are buffered in an additional native send queue.

Android's constructor and completion model are unchanged. The new iOS constructor selects four Normal links (including setup), three in Saver and the existing iOS power policy. Readiness operations reject Android owners. Only real inbound traffic or an actual readiness callback refreshes iOS liveness; property polling and outgoing submissions do not. Fifteen seconds without either closes the link. All callback entry points advance time before processing new data, so a suspension/foreground jump cannot revive expired work. The clock uses `mach_continuous_time`, including suspension. Native scheduler deadlines and initial HELLO timeout remain independent.

## Resource and lifecycle limits

The pure production `IOSGattDriver` owns at most four setup/ready records. Pre-admission reception stages at most two bounded values per peer (eight values total); oversized input retains its reported length without copying its body. Excess staged values drop newest. Callbacks reference monotonic driver IDs; closed IDs cannot recreate links or retransmit work. A first qualifying CHAT/ANNOUNCE is required within twenty seconds of reservation, followed by a five-minute observed-address blacklist on failure. The blacklist holds at most 64 entries and refuses new admission when full until entries expire; it never discards a live ban to make space. The application must emit its initial valid public ANNOUNCE within this window. Opaque or pending verification is not qualifying content.

The native adapter retains at most 64 discovered peripheral records, four total logical connections, no packet log and no private keys. Discovery is filtered by the service UUID. Mode/charging changes reuse the existing core owner; cap shrink returns explicit cancellation/close effects. Reconnect after a manager reset waits five seconds and never resets node/address credits. Discovery records and provider objects are process-local, not persisted identity claims.

CoreBluetooth callbacks lack an application connection-generation field. Teardown conservatively replaces the affected role's manager epoch and closes its other logical connections too. Old manager/object callbacks cannot be attributed to a reused connection. This trades continuity for unambiguous cleanup; physical churn/coverage consequences must be assessed in MC-027. It does not claim to force a remote central's physical radio disconnect through an unavailable iOS API. Replacing the peripheral service invalidates this adapter's old characteristic objects and subscriptions.

Restored central objects are bounded by admission and start fresh HELLO with the current protected core; excess or refused objects are cancelled. Restored peripheral services/subscriptions are discarded before publishing fresh characteristic objects. No Rust session, queued message or unlocked provider is restored from an OS dictionary. A locked/unavailable provider stops the generation and requires the application to reopen its protected owner. Foregrounding advances deadlines and requests feature catch-up. The timer never claims continuous background execution.

States distinguish starting, foreground, limited background participation, restoration/recovery, permission denial, radio off, locked/unavailable and stopped. Protection loss, termination and explicit stop clear owned resources and notification observers. Force-quit recovery requires a new user launch; background delivery and restoration timing are conditional. Android discovery of a backgrounded iPhone remains unsupported in the baseline. No Live Activity exception or stronger advertising privilege is assumed.

## Validation and remaining evidence

Rust tests cover iOS caps including setup, Saver shrink, Android timeout preservation, repeated backpressure with unchanged bytes, stale tokens, real inbound versus property-only liveness, charged attempts, absolute expiry, and deferred SYNC wrapper exchange. Existing Android and core suites remain regression gates.

`tests/bench/ios/DriverChecks.swift` executes the production Swift driver against the actual Rust library and a bounded native-operation double. It exercises both roles, base logical kinds, whole/fragmented traffic, SYNC item/marker deferral, queue-full/readiness, directional-capacity refusal/change, bounded early input, caps, power cancellation, stale callbacks, restoration reset and suspend/foreground time jumps. The FFI trace also exercises actual HELLO/proof/crypto vectors. Controlled callbacks are not actual OS restoration or radio evidence.

The existing Mac job compiles the driver and tests with Swift 6 warnings as errors, runs them, builds the app/BLE/security projects with Xcode 16.4, and executes security/storage regressions. Android native/FFI checks apply because the shared exported surface changed. Run Rust formatting/clippy/debug/release/build/cargo-deny, ticketboard regeneration/default/unit checks and diff check. Exact source revisions and outcomes belong in the ticket/PR; no pending checks are counted passed.

MC-027 retains real iPhone/Android role, backpressure, capacity, background, suspension, restoration, force-quit and battery scenarios. MC-044 retains physical protected-storage acceptance. Synthetic hosts/emulators and unsigned compilation do not certify those scenarios.
